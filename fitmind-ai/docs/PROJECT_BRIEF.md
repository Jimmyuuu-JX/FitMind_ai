# FitMind AI 项目说明书（PROJECT_BRIEF.md）

> 这是 FitMind AI 的源头文档：产品是什么、为谁做、做什么不做什么、按什么规模设计。
> 架构、API、数据库、AI 决策等子文档都以它为前提；与它冲突时，先改这份，再改子文档。
>
> 本文只写产品定位与长期约束，不镜像代码。实现细节看 [`INDEX.md`](./INDEX.md) 指向的子文档和源码。

---

## 1. 一句话定位

**FitMind AI 是给认真练力量的人用的训练日志，自带一个只根据你自己的记录说话的教练。**

日志是地基：记得快、查得到、算得准。教练是差异点：它的每一句判断都能追溯到用户自己的训练记录和确定性计算结果，而不是模型的常识或想象。

---

## 2. 为谁做，解决什么

### 用户

- 有规律力量训练习惯的人（每周约 3–5 练），愿意逐组记录重量、次数和主观强度。
- 想从自己的记录里得到反馈，而不是通用的健身文章。

### 要回答的问题

- 「我今天该练什么，还是该休息？」
- 「这个动作几周没涨了，是停滞还是正常波动？」
- 「我最近哪里练多了、哪里练少了？」
- 「下周怎么安排？」

回答这些问题需要同时看用户的历史数据和训练学常识。手动统计太费时间；通用聊天模型不知道用户的数据。

### 产品阶段

FitMind AI 是一个持续运营的小产品，不是演示项目。功能取舍以「真实用户长期使用是否更好」为准。

## 3. 产品原则

这五条是长期约束。新功能与其中任何一条冲突时，改功能，不改原则；确实要改原则时，先改本节。

1. **数字由代码算，模型不算数。** 训练量、进展、肌群负荷、依从度等所有数值来自确定性计算层。模型可以选择看哪些数据、如何解释，但不是数值的事实来源。
2. **回答带依据。** 教练的结论要能展开看到它引用了哪些记录和计算结果；没有数据支撑时明说没有，不编。
3. **写入必须由人确认。** 模型可以起草训练记录、计划和修改建议，但任何落库的变更都要用户看过并确认。
4. **伤痛和医疗问题不给建议。** 涉及疼痛、用药、诊断的提问在到达模型之前就分流，给出就医提示。产品不做医学判断。
5. **数据属于用户。** 用户能看到、导出口径清楚、能分类删除自己的数据；敏感健康数据的使用以单独同意为前提，可随时撤回。

## 4. 功能边界

### 核心：持续投入

| 功能         | 说明                                                                   |
| ------------ | ---------------------------------------------------------------------- |
| 训练记录     | 语音、自由文本、手动三种录入；训练中的逐组编辑、热身组、主观强度、休息计时 |
| 历史与分析   | 日历与列表、训练量与肌群负荷、动作进展与平台期、周趋势                   |
| 动作库       | 动作词典、别名匹配、动作—肌群贡献权重                                    |
| 教练对话     | 基于用户记录的问答与建议，见第 5 节                                      |
| 周计划       | 按训练天数、时长、器械、目标和伤病生成草案，可编辑后接受，并对比计划与实际 |
| 健康数据联动 | 经期记录和身体数据在用户授权后供教练参考，见第 6 节                      |

### 支撑：保留，不主动扩展

RM 计算器、训练备忘录、周报摘要、收藏洞察、产品反馈、训练档案（目标、器械、伤病限制）。

### 不做

- 医学诊断、康复处方、用药建议。
- 经期或排卵预测。
- 饮食与营养管理。
- 社交、排行榜、内容社区。
- 教练对训练以外话题的闲聊。
- 把工具层对外暴露为 MCP Server。

## 5. 教练：模型主导，事实由计算层把关

### 目标形态

教练是一个带工具的对话模型：

- **带对话历史。** 用户可以追问、纠正、接着上一句说。
- **模型自己决定查什么。** 它按需多次调用只读工具（训练汇总、动作进展、肌群负荷、周报、计划依从度、动作知识检索等），直到有足够依据再回答；循环有步数和成本上限。
- **解释由模型写。** 表达、取舍和建议的组织交给模型，不再由固定模板拼接。
- **事实仍由计算层给。** 工具返回的是计算结论和它依据的数据点，不是让模型自己去算的原始日志。
- **数字核对保留。** 回答中的数值必须能在本轮工具结果里找到，核对结果对用户可见。
- **写操作走草稿。** 记录训练、生成或修改计划等写入，模型只产出草稿，由用户在界面上确认后落库。
- **安全分流在模型之前。** 伤痛与医疗类提问不进入模型。

### 规则层的位置

关键词路由、固定答案模板这类规则只在两种情况下保留：作为模型不可用或超出预算时的降级路径，以及作为评测的对照基线。它们不是主路径。

### 模型提供方

模型通过提供方适配层接入，型号由环境配置决定，代码中不写死型号。境内实例和海外实例可以使用不同提供方；更换提供方不应改动教练的业务逻辑。评测集是更换模型或提示词时的回归门禁。

### 现状与差距

当前实现以规则路由为主，模型每轮最多选择一个工具，答案由模板生成，请求不带对话历史。从现状到上述目标形态的改造由 [`roadmap.md`](./roadmap.md) 跟踪；当前结构见 [`architecture.md`](./architecture.md)，历次决策见 [`ai-decisions.md`](./ai-decisions.md)。

## 6. 敏感健康数据

经期记录和身体数据（体重、围度等）属于敏感健康数据。它们接入教练，是为了让建议更贴合用户当下的状态，例如结合体重趋势解读力量变化，或在用户记录了经期的日子里解释状态波动、调整强度建议。

约束：

- **单独同意。** 教练读取这两类数据以用户对敏感健康数据的明确同意为前提；未同意或已撤回时，教练看不到，产品其余功能照常可用。
- **只引用已记录的事实。** 教练可以引用用户记下的日期和数值，不推算周期，不做医学解读。
- **最小够用。** 只把回答当前问题需要的字段交给模型；工具调用日志不记录这类数据的具体数值。
- **可分类删除。** 用户可以单独删除某一类健康数据，或一次性删除全部，删除后教练不再引用。
- **跨境告知。** 数据或模型请求离开用户所在法域时，按实例的数据驻留配置要求单独的跨境同意。

## 7. 规模阶段与预留

### 当前阶段

**按几个人到几十人的实际使用来运营**：邀请制注册，单实例部署，由一名维护者负责发布和排障。这一阶段不为还没出现的负载提前搭基础设施。

### 设计要求

**按更多人使用来设计**：凡是人多之后必须更换的部分，现在就放在明确的接缝后面，更换时不需要改业务逻辑。下表是已知的接缝；新增功能如果引入了「只适合几个人用」的做法，要在这里登记。

| 方面           | 当前做法                                           | 人多之后要变的                             | 预留方式                                                     |
| -------------- | -------------------------------------------------- | ------------------------------------------ | ------------------------------------------------------------ |
| 注册           | 邀请制，由环境开关控制                             | 开放注册需要找回密码、邮箱验证和滥用防护   | 注册策略由服务端下发，客户端不写死                           |
| 数据隔离       | 所有用户资源按已认证用户约束                       | 不变                                       | 这是硬规则，见 `AGENTS.md`；跨用户与不存在的资源返回相同结果 |
| 会话           | 无服务端会话状态的 HttpOnly cookie                 | 不变，天然支持多实例                       | 服务端进程不保存用户会话                                     |
| 数据库         | 托管 PostgreSQL 的入门档，恢复历史短               | 升档、独立备份与恢复演练、只读副本         | 所有 SQL 经 repository 与进程级共享连接池；迁移按顺序可重放  |
| 限流与配额     | 进程内存计数                                       | 多实例时要换成共享存储                     | 限流器是接口，换实现不改调用方                               |
| 模型成本       | 全实例的每日调用与费用上限，超出后降级             | 按用户的配额，必要时与付费档位挂钩         | 预算策略独立于教练编排；每轮记录用量与成本                   |
| 模型提供方     | 按实例用环境变量配置                               | 多提供方路由、按任务选型                   | 提供方适配层；型号不写死；评测集做回归门禁                   |
| 定时任务       | 受密钥保护的端点，定时方按实例另配 | 任务量变大后换成队列                       | 任务入口是幂等的 HTTP 端点，与触发方式解耦                   |
| 部署           | 境内单机容器；海外无服务器托管                     | 多实例与滚动发布                           | 同一份代码，差异全部来自运行时配置                           |
| 可观测         | 结构化日志与定期汇总脚本                           | 集中式指标、告警、追踪                     | 每轮教练请求已有结构化观测记录，可直接对接采集               |
| 合规           | 同意项带版本；数据驻留与跨境同意由配置决定         | 公开运营需要补齐的主体、协议与告知         | 同意是带版本的独立模型，新增同意项不改账户结构               |
| 交接与多人协作 | 一名维护者                                         | 他人接手或加入                             | 见下                                                         |

### 为交接预留

- 进入项目的路径固定：`AGENTS.md` → 本文 → [`INDEX.md`](./INDEX.md) 按任务指向的子文档。
- 容易悄悄漂移的约定用测试守住，而不是只写在文档里（例如 API 契约与路由的双向断言）。
- 决策理由记在 [`ai-decisions.md`](./ai-decisions.md)，文档只写代码自己说不清的东西：为什么这么定、口径是什么、踩过什么坑。
- 发布步骤可按文档重放，不依赖维护者的记忆，见 [`production-smoke-checklist.md`](./production-smoke-checklist.md) 与 `deploy/README.md`。

## 9. 安全与合规

- **传输与存储。** 全程 HTTPS；训练记录与健康数据按个人健康数据对待。
- **认证。** HttpOnly、Secure、SameSite 的 cookie 会话；密码只存哈希。
- **同意。** 同意项带版本，条款更新后要求补签；跨境传输与敏感健康数据各自单独同意。
- **删除权。** 用户可以删除账户，也可以分类删除健康数据。入口应当在个人页里能直接找到。
- **健康建议风险。** 伤痛与医疗类提问触发安全分流；教练的建议标明不构成医疗、康复或专业训练处方；知识库不收录诊断类内容。
- **提示注入。** 用户输入只作为用户消息，不拼进系统提示；检索到的知识和工具结果按数据对待，不按指令执行。
- **工具白名单。** 模型只能调用预先注册的工具，参数经运行时校验；对话路径上没有直接写库的工具。
- **限流与成本上限。** 认证、教练和按 IP 的请求都有速率限制；模型调用有每日预算，超出后降级而不是报错。具体数值见中间件与预算策略源码。

## 10. 性能与体验目标

| 指标                   | 目标    |
| ---------------------- | ------- |
| 首屏加载               | < 2s    |
| 教练首字时间           | < 1.5s  |
| 单次工具调用端到端     | < 5s    |
| 流式渲染               | 不卡顿  |
| 训练记录列表（100 条） | < 500ms |

实测方法与结果记录在 [`production-smoke-checklist.md`](./production-smoke-checklist.md)。教练改为多步工具循环后，首字时间按「开始输出第一段可读内容」计，中间的工具步骤要对用户可见。
